# Hypercube Office 0.2.0: full audit

Audit of `main` at commit `c24a089` (the 0.2.0 release), done on 2026-10-09. It covers four
questions:

1. Does the app work? (tests, a real-app run, CI)
2. What can be removed to make it lighter and more responsive?
3. How does it compare with [PDFcraft](https://github.com/storytold/pdfcraft) for viewing and
   editing PDFs?
4. Should the app, or a part of it, be rebuilt in Rust?

**Follow-up (2026-10-09):** after the owner's answers, wheel-zoom lag, long-document scrolling,
the cost of the 21 languages and the app's network use were measured in more depth; see
[v0.2.0-followup.md](v0.2.0-followup.md), which also updates the plan.

Every number below was measured during this audit unless it says otherwise. The step-by-step plan
is in [section 7](#7-step-by-step-plan) and the open questions are in
[section 8](#8-questions-for-you).

## 1. Summary

**The app is in good health.** About 13,400 unit tests pass, lint and type checks are clean, CI is
green, and 16 of the 19 PDF and core end-to-end tests passed on the first run (the other 3 are
explained below). The AI, sign-in and telemetry code from GenOffice is gone, apart from a few
small leftovers listed in [4.3](#43-leftovers-from-genoffice-and-unused-code).

**The biggest problems are not the language the app is written in.** They are a handful of
architecture choices in the PDF side, each one measurable and fixable:

| #   | Finding                                                                                                                    | Measured effect                                                                 |
| --- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1   | Saving a PDF rewrites the whole file, which **breaks digital signatures** without a warning                                | A signature that was "not modified since signing" became "Signature is invalid" |
| 2   | Every PDF open makes the shared main process fully re-parse the file with pdf-lib to read one private value                | Removing that one call made the first page appear **2× sooner** (3.4 s → 1.7 s) |
| 3   | Four separate PDF engines are bundled (pdf.js, pdf-lib, PDFium, MuPDF), and pdf-lib has had no release since November 2021 | Saves with pdf-lib took 4.8 s vs 0.9 s with MuPDF on a 700-page file            |
| 4   | Heavy PDF work runs on the Electron main process, which every tab and window shares                                        | Open, save and edit previews freeze all tabs while they run                     |
| 5   | The PDF viewer is one 9,400-line React component with 144 state variables and no memoization                               | 22 long tasks (2.2 s of jank) while scrolling 40 screens of a 700-page file     |
| 6   | The installer ships about 26 MB it never uses, and every editor loads 21 UI languages at start                             | 11 MB of unused files and 15 MB of duplicates in the build output               |

**On Rust: do not rebuild the app in Rust.** Fix the items above first; they give most of the
speed and memory gains for a small fraction of the cost. A narrow Rust "PDF engine helper"
process (the app already has one for spreadsheets) is a sensible later step if the targets are
still not met on the 4 GB laptop. PDFcraft is impressive but is about ten days old, and it is
weakest at exactly what Hypercube does best (editing existing text). Details in
[section 6](#6-should-hypercube-be-rebuilt-in-rust).

## 2. How the audit was done

- **Code review** of all 21 workspaces (about 571,000 lines of source plus 249,000 lines of
  tests), with the PDF viewer, PDF editor, PDF tools, shell and packaging read in depth.
- **Unit tests, lint and type checks** for every workspace.
- **A production build** (`npm run build:all`), then the **real app** driven by Playwright under
  a virtual display, with three PDFs: the 14-page pdf.js sample paper (1 MB), and that paper
  repeated to 700 pages (50 MB) and 2,100 pages (152 MB).
- **Engine benchmarks** in Node for pdf.js, pdf-lib, PDFium (WASM), MuPDF (WASM) and the
  PDFcraft command-line tool built from source.
- **An A/B test**: one suspected slow call was switched off in a local build (never committed)
  and the real app was measured with and without it.
- **A dead-code scan** with knip, checked by hand.
- **A digital-signature test**: a PDF signed with PDFcraft's self-signed ID was saved the same
  way the Hypercube editor saves, then validated again.

**Caveat about the numbers.** The machine was a 4-core Linux virtual machine with 15 GB of RAM
and no GPU. Windows 10 on a 4 GB laptop will be slower in absolute terms. Treat the numbers as
ratios ("twice as fast", "grows with page count"), and re-measure on the target laptop before
setting targets (see question 1).

## 4. Findings in detail

Severity: **Critical** = can damage a user's document or trust; **High** = clearly hurts speed or
memory on a 4 GB laptop; **Medium** = worth doing; **Low** = tidy-up.

### 4.1 Correctness and safety

**C1 (Critical). Saving breaks digital signatures, silently.**
Every editor save rebuilds the whole file (`apps/pdf/src/main/save-pdf.ts:1123` `savePdfToPath` →
`applySaveRequest` → pdf-lib `save()`), and text edits go through PDFium's full `SaveAsCopy`.
A certificate signature covers the exact bytes of the file, so any rewrite invalidates it. There is
no check for signed files anywhere in `apps/pdf/src`. In the test, a signed PDF went from
"This document has not been modified since this signature was applied" to "Signature is invalid"
after adding one highlight. Signed lab reports, prescriptions, consent forms and contracts are
common, so this matters.

- Now: detect a signed document (`/ByteRange` in a signature field) on open and warn before the
  first edit, offering "Save as a copy".
- Properly: save signed documents incrementally (append changes after the original bytes). MuPDF
  supports this (`saveToBuffer('incremental')`); that is how Acrobat and PDFcraft keep signatures
  valid.

**C2 (Medium). Every save is a full rewrite.** Besides signatures, a full rewrite is slower on big
files, can drop parts pdf-lib does not understand, and loses the document's revision history.
Incremental saves fix all three (see [step 3](#step-3-consolidate-the-pdf-engines-2-to-4-weeks)).

**C3 (Medium, raised from Low). Flaky `e2e/pdf-text-box.spec.ts`, and a duplicate-save bug behind
it.** Wait for the Comments panel to show no "Unsaved" row before counting rows (around line 60).
Behind the flake: a save requested while the previous save's reload was settling could start from
a screen update that did not yet include the reload, and wrote the just-saved edits again. Fixed in
step 1 by starting a queued save only once the finished save's reload is on screen.
**Follow-up (2026-10-26):** that fix covered queued saves only. A flaky
`e2e/pdf-signed-save.spec.ts` turned up two more ways to write the first edit twice, both in the few
milliseconds between a save finishing and its reload reaching the screen: pressing Save in that
gap started a save from the old screen state, and adding an edit in that gap put the just-saved
edits back on the pending list. Both are fixed, with a regression test for the first.

### 4.2 Speed and memory

**H1 (High). Every open re-parses the whole file with pdf-lib, on the main process.**
`App.tsx:1113` calls `listStaticFormFills`, which reads the file again and runs pdf-lib's
`PDFDocument.load` on all of it (`save-pdf.ts:66-67`) to read one private catalog key
(`GenOfficeStaticFormFills`). pdf-lib parses every object up front:

| File        | pdf-lib full parse | MuPDF open + read the key |
| ----------- | -----------------: | ------------------------: |
| 14 pages    |             149 ms |                     17 ms |
| 700 pages   |  1,635 ms (+77 MB) |                    173 ms |
| 2,100 pages | 5,330 ms (+203 MB) |                    596 ms |

Because the main process serves every tab, the whole app stalls for that time. The A/B test
showed this single call is about half of the time to the first page on large files. Fix: read the
key with MuPDF in a worker, or skip the call when the file was never saved by Hypercube.

**H2 (High). Heavy PDF work runs on the main process.** Saves (pdf-lib), text and image editing,
redaction and the live edit preview (PDFium) all run in the Electron main process
(`apps/pdf/src/main/*`). The PDF Tools already do this right: MuPDF runs in a worker thread
(`apps/shell/src/main/pdf-tools/worker.ts`). The editor should do the same. Also, every edit
preview re-reads the file from disk and re-opens it in PDFium (`pdf-main.ts:1144`), which costs
about 110 ms per call on the 700-page file and 300 ms on the 2,100-page file before any drawing.
Keeping the open document cached in the worker removes that.

**H3 (High). The viewer does all-pages work before showing page 1.** `App.tsx:1090` awaits
`getPage()` for every page in turn, and `buildFormCatalog` (`form-catalog.ts:201`) then loads
every page's annotations, all before the first page is drawn. In-process this is only about 0.2 ms
per page, but in the app each call is a round trip to the pdf.js worker. Show page 1 first, size
the rest from page 1 until they are known, and use `getFieldObjects()` (one call, `null` when the
file has no form) instead of scanning every page.

**H4 (High). One very large React component.** `apps/pdf/src/renderer/App.tsx` is 9,402 lines with
144 `useState`, 39 `useEffect` and no `React.memo` anywhere in the PDF renderer. Any state change
(for example the pointer position while placing a text box, `App.tsx:7330`) re-renders the whole
tree, including a wrapper for every page of the document. That is where the long tasks during
scrolling come from. Split it into a page list, toolbars and panels; memoize each page row; keep
fast-changing pointer state inside the page layer.

**H5 (High). The main process loads every editor at start.** `apps/shell/src/main/index.ts:85-180`
and `tab-manager.ts:6-46` statically import the main-process code of all six editors, so the shell
main bundle is 8.3 MB and idles at 294 MB. Load each editor's back end with `import()` the first
time its tab opens.

**M1 (Medium). Large page bitmaps and no tiling at deep zoom.** `MAX_PAGE_RENDER_PIXELS` is 48
million pixels (`view-config.ts:71`), about 190 MB for one page bitmap. pdf.js's own viewer caps
at about 33 million and draws only the visible part at high zoom; PDFcraft renders tiles. For a
4 GB laptop, cap around 16 million and render the visible area at high zoom.

**M2 (Medium). Every editor loads all 21 UI languages.** The string tables are 111,000 lines
(5.7 MB of source), and each editor imports all 21 languages eagerly (for example
`apps/sheets/src/renderer/i18n/strings-app.ts`). Your plan needs English now and Arabic later.
Either drop the others or load only the active language with `import()`.

**M3 (Medium). Very large editor bundles.** Built renderer JavaScript: Sheets 30 MB (one 19 MB
file), Markdown 13.6 MB, Docs 10.6 MB, PDF 4.4 MB, Slides 4.2 MB. The Sheets size is why the shell
pre-loads a hidden spare Sheets tab (`tab-manager.ts:118`), which costs a whole renderer process
of memory. Splitting the Sheets bundle and loading features on demand would let that hack go.

**M4 (Medium). Two dependency advisories rated high.** `npm audit` reports `prosemirror-view`
1.42.1 (below 1.42.3: a cross-site scripting issue in paste handling, used by Docs and Markdown)
and `@grpc/grpc-js` 1.14.4 (pulled in by Univer's protocol package; the app does not use gRPC
offline, so the risk is low). Both have fixes within the same major version: refresh the lockfile.
Three low-rated advisories (DOMPurify, KaTeX, Mermaid) can follow.

**L1 (Low). Legacy pdf.js build.** The viewer imports `pdfjs-dist/legacy/build/pdf.mjs`. The
legacy build carries polyfills for old browsers; Electron's Chromium does not need them. Check
whether any test depends on it, then switch to the modern build.

### 4.4 Privacy and the "offline" promise

There is no telemetry and no automatic network use. The renderers have strict content security
policies that block remote content. The main process still downloads web images in three cases,
always after a user action:

- pasting web content with images into Docs (`apps/docs/src/main/docs-main.ts:3705`);
- exporting Markdown to Word when it links to web images (`apps/markdown/src/main/markdown-main.ts:549`);
- HTML documents with linked web images (`apps/html/src/main/html-main.ts:950`).

`PRIVACY.md` covers most of this, but `README.md` says the app "never connects to the internet"
apart from the update check, and neither file mentions the in-app installer download added in
0.2.0. Decide whether these should stay (question 6) and make both documents say the same thing.

### 4.6 What is already good

- A large test suite (about 13,400 unit tests plus 92 end-to-end specs) and CI that installs and
  uninstalls the real Windows installer.
- Careful Electron security: context isolation, sandboxed renderers, strict content security
  policies, a server-side request forgery guard on downloads, and atomic file writes.
- An honest update installer: opt-in, SHA-256 checked, and clear about what an unsigned installer
  can and cannot guarantee.
- The PDF Tools already run MuPDF off the main thread, and some editing code loads PDFium only
  when needed. Those patterns just need to spread to the rest of the PDF editor.

## 5. Comparison with PDFcraft

PDFcraft is a PDF workbench written entirely in Rust: about 126,000 lines of its own code plus
85,000 lines of vendored libraries, an egui interface, MIT or Apache-2.0 license. By its own
roadmap, work started on 2026-09-30 and it is "about 30–35% of the effort" towards Acrobat parity.

Rust: MuPDF, which Hypercube already ships, does both.

## 6. Should Hypercube be rebuilt in Rust?

| Option                                                                  | Gains                                                                                  | Costs and risks                                                                                                                                                                         | Verdict                                             |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **A. Rewrite everything in Rust** (like PDFcraft)                       | Small installer, low memory, native speed                                              | Replace ~571,000 lines. Docs, Sheets and Slides depend on web editing libraries (TipTap/ProseMirror, Univer, Konva) with no Rust equal. Lose the RTL interface Chromium gives for free. | **No**                                              |
| **B. Swap the PDF tab for PDFcraft**                                    | Its viewer, signatures and safe saves                                                  | Two interface toolkits in one app; lose in-place text editing, Office conversion and Windows OCR; a ten-day-old project changing daily                                                  | **Not now.** Revisit in 6–12 months                 |
| **C. Fix the architecture in TypeScript** (steps 1–4 below)             | Measured: 2× faster first page from one fix; less memory; no frozen tabs               | Weeks, not months; no new language                                                                                                                                                      | **Yes, first**                                      |
| **D. Add a Rust "PDF engine helper" process** (like the Sheets sidecar) | Native MuPDF/PDFium: faster drawing, several threads, document kept open, lower memory | A second build toolchain on the PDF side (already present for Sheets); a message protocol to maintain                                                                                   | **Yes, later, if C is not enough**                  |
| **E. Move from Electron to Tauri** (Rust shell, Windows WebView2)       | Installer could drop from ~140 MB to well under half                                   | Rewrite all main-process code (the shell plus six editor back ends, about 45,000 lines) against new APIs; WebView2 behaves differently from bundled Chromium                            | **Only if installer size becomes the top priority** |

In short, the slowness you feel comes from what the code does (parsing whole files repeatedly,
blocking the shared process, re-rendering everything), not from JavaScript itself. The engines
that do the heavy lifting (pdf.js, PDFium, MuPDF) are already C or C++ compiled to WebAssembly.
Rust would help most as option D, a narrow engine helper, after option C.

## 7. Step-by-step plan

Sizes: **S** = a day or less, **M** = a few days, **L** = one to two weeks (AI-assisted pace).

### Step 1: Quick wins (about one week)

1. **Warn before editing a signed PDF** and offer "Save as a copy" (C1). **S**
2. **Stop the full pdf-lib parse on every open** (H1). Read the private key with MuPDF in a
   worker, or skip it for files Hypercube never saved. **S**, measured 2× faster first page.
3. **Trim the installer** (4.5): exclude `main/**` from the module copies, share fonts and the
   pdf.js worker. **S**, about 26 MB less.
4. **Remove the leftovers** in 4.3 (Genspark headers, AI prompts, font CDN code, unused file and
   dependencies) and refresh the lockfile for the advisories in M4. **S**
5. **Fix the flaky `pdf-text-box` test** (C3). **S**
6. **Make `README.md` and `PRIVACY.md` agree** on network use (4.4). **S**

### Step 2: A responsive PDF viewer and editor (one to two weeks)

1. **Move the editor's PDF work into a worker** (H2), following the PDF Tools pattern, and keep
   each open document cached there instead of re-reading the file per call. **M**
2. **Show page 1 first** (H3); use `getFieldObjects()` for forms. **S**
3. **Split `App.tsx`** and memoize page rows (H4). **L**
4. **Cap the page bitmap and render only the visible area at high zoom** (M1). **M**
5. **Add a large-PDF performance test to CI** (open a generated 700-page file and fail if the
   first page takes longer than an agreed budget), and commit a small real-world PDF test set as
   the plan's Phase 0 intended. **S**

### Step 3: Consolidate the PDF engines (two to four weeks)

1. **Replace pdf-lib with MuPDF** for saves and page operations in the editor, with
   **incremental saves** by default. This keeps signatures valid, is about 5× faster on large
   files (4.8 s vs 0.9 s measured) and removes an unmaintained library. **L**
2. **Keep PDFium** for in-place text and image editing, where it is the strongest option.
3. **Keep pdf.js** for drawing pages for now; reconsider after step 5.

That takes the PDF side from four engines to three, and later two.

### Step 4: A lighter shell (one to two weeks)

1. **Load each editor's back end on first use** (H5). **M**
2. **Load only the active UI language** (M2), or drop the languages you will not ship. **M**
3. **Decide what happens to the Office editors** (question 2): keep them built in, make them an
   optional download, or ship a PDF-only edition. **Decision**
4. **Split the Sheets bundle** so the hidden spare Sheets tab is no longer needed (M3). **L**

### Step 5: Measure on the real laptop, then decide on Rust

Re-run the measurements in section 3.3 on the 4 GB Windows laptop. If opening and scrolling meet
the plan's targets (app open under 2 s, a 100-page PDF visible under 1 s), stop. If not, build
option D: a Rust helper process that wraps native MuPDF (and PDFium for editing), draws tiles on
several threads and keeps documents open, while the React interface stays as it is.

### Step 6: Watch PDFcraft

Its code is MIT/Apache, so parts of it may be reused in this AGPL app later, for example its
signature crate (PAdES signing and validation) or its optimizer. Wait until it has its own
renderer and clean nightly fuzzing before depending on it.

## Appendix: method notes

- Large test files were made by repeating the pdf.js sample paper (`compressed.tracemonkey-pldi-09.pdf`)
  with MuPDF, sharing resources within each copy.
- Real-app runs used the repo's own e2e launcher (`e2e/helpers.ts`) with
  `GENOFFICE_NO_SPARE_VIEW=1`, under Xvfb with `--disable-gpu`; memory is the working set reported
  by `app.getAppMetrics()`.
- The A/B build changed only `readStaticFormFills` (behind an environment variable) and was
  reverted after measuring; nothing from it is committed.
- PDFcraft was built from `main` at commit `d4d2e83` with `cargo build --release -p pdfcraft-cli`.
- The dead-code scan used knip 5 with the Electron entry points (`src/main/index.ts`, preloads and
  renderer `main.tsx`) declared; its unused-file list was checked by hand, which removed false
  positives such as `packages/pdf2docx/src/ocr-vision.ts`.
